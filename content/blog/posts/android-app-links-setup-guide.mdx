## What Are Android App Links?

Think of Android App Links as a verified handshake between your website and your app. You place a special file on your website that says "this app owns this domain." Android reads that file, trusts it, and from then on routes any link to your domain straight into your app automatically.

The technical name for that file is `assetlinks.json`. It lives at a specific location on your server and contains your app's unique certificate fingerprint. That fingerprint is how Android knows your app is the real owner of the domain, not some impersonator.

### App Links vs Other Linking Methods

Not all Android deep links work the same way. Here is a clear breakdown:

| What you want to know | App Links (https://) | Intent Filter (unverified) | Custom Scheme (myapp://) |
|---|---|---|---|
| Does it show the "Open with" popup? | Never | Every single time | Rarely |
| What happens if the app is not installed? | Opens Chrome | Opens Chrome | Shows an error |
| Is domain ownership verified? | Yes, cryptographically | No | No |
| Which Android version supports it? | Android 6.0 and above | All versions | All versions |
| Works inside email apps? | Yes | Yes | Sometimes |

App Links are the only method that gives you a seamless, popup-free experience every time.

## The Three Things You Need

Before jumping into the steps, here is the big picture. Android App Links require three pieces working together:

If any one of these three is missing or incorrect, App Links will not work. Let's build each one.

## Step 1: Create Your assetlinks.json File

This is the verification file that lives on your website. Android fetches it automatically when someone installs your app, to confirm your app really owns your domain.

Host the file at this exact path on your server:

```
https://example.com/.well-known/assetlinks.json
```

### What the file looks like

```json
[
  {
    "relation": ["delegate_permission/common.handle_all_urls"],
    "target": {
      "namespace": "android_app",
      "package_name": "com.yourcompany.yourapp",
      "sha256_cert_fingerprints": [
        "FA:C6:17:45:DC:09:03:78:6F:B9:ED:E6:2A:96:2B:39:9F:73:48:F0:BB:6F:89:9B:83:32:66:75:91:03:3B:9C"
      ]
    }
  }
]
```

Replace `com.yourcompany.yourapp` with your actual package name and swap the SHA-256 fingerprint with yours (how to get that is covered right below).

### Getting the correct SHA-256 fingerprint

This is where 18% of Android developers get it wrong. There are two different fingerprints — one for your local debug build and one for the live app on Google Play. You need the Google Play one.

**The easiest way: Get it from Google Play Console**

1. Open Google Play Console and select your app
2. Go to **Release** then **Setup** then **App Integrity**
3. Click the **App signing** tab
4. Copy the **SHA-256 certificate fingerprint** shown under "App signing key certificate"

That is the fingerprint you paste into `assetlinks.json`.

**If you manage your own keystore:**

```bash
keytool -list -v \
  -keystore /path/to/your.keystore \
  -alias your-key-alias \
  -storepass your-password
```

Look for the line starting with `SHA256:` in the output.

**If you want to check an APK file directly:**

```bash
apksigner verify --print-certs your-app.apk | grep SHA-256
```

### One important note about serving this file

Your server must return the file with a `Content-Type: application/json` header and no redirects. Android does not follow 301 or 302 redirects when fetching this file. If your `example.com` redirects to `www.example.com`, you need to host the file on both domains separately.

## Step 2: Update Your AndroidManifest.xml

Now tell your Android app to look for that verification file. Open `AndroidManifest.xml` and add a new intent filter to your main Activity with `android:autoVerify="true"`.

```xml
<activity
    android:name=".MainActivity"
    android:exported="true">

    <!-- Regular app launcher intent, keep this as is -->
    <intent-filter>
        <action android:name="android.intent.action.MAIN" />
        <category android:name="android.intent.category.LAUNCHER" />
    </intent-filter>

    <!-- App Links intent filter, this is the new part -->
    <intent-filter android:autoVerify="true">
        <action android:name="android.intent.action.VIEW" />
        <category android:name="android.intent.category.DEFAULT" />
        <category android:name="android.intent.category.BROWSABLE" />

        <!-- Add both with and without www -->
        <data
            android:scheme="https"
            android:host="example.com" />
        <data
            android:scheme="https"
            android:host="www.example.com" />
    </intent-filter>

</activity>
```

The `android:autoVerify="true"` part is critical. Without it, Android skips verification and falls back to showing the "Open with" popup. Do not skip it.

## Step 3: Handle the Incoming Link in Kotlin

When a link successfully routes to your app, your code needs to read it and send the user to the right screen. Here is a clean handler:

```kotlin
class MainActivity : AppCompatActivity() {

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        handleDeepLink(intent)
    }

    override fun onNewIntent(intent: Intent) {
        super.onNewIntent(intent)
        handleDeepLink(intent)
    }

    private fun handleDeepLink(intent: Intent) {
        if (intent.action != Intent.ACTION_VIEW) return
        val uri = intent.data ?: return

        when {
            uri.pathSegments.firstOrNull() == "products" -> {
                val productId = uri.pathSegments.getOrNull(1)
                navigateToProduct(productId)
            }
            uri.pathSegments.firstOrNull() == "user" -> {
                val userId = uri.pathSegments.getOrNull(1)
                navigateToProfile(userId)
            }
            else -> {
                navigateToHome()
            }
        }
    }
}
```

## Step 4: Verify That Everything Is Working

Do not skip this step. A lot of App Links setups look fine but have a small error that only shows up during verification.

### Check with Google's verification tool

Open this URL in a browser, replacing `example.com` with your actual domain:

```
https://digitalassetlinks.googleapis.com/v1/statements:list?source.web.site=https://example.com&relation=delegate_permission/common.handle_all_urls
```

If you see `"matched": true` in the response, your file is valid. If the response is empty or shows an error, something is wrong with your `assetlinks.json`.

### Check on a real device with ADB

```bash
# Trigger verification manually
adb shell pm set-app-links --package com.yourcompany.yourapp 2 example.com

# Then check the result
adb shell pm get-app-links com.yourcompany.yourapp
```

You want to see `verified` next to each domain. If you see `none` or `legacy_failure`, there is an issue that needs fixing before launch.

### Simulate a real link tap

```bash
adb shell am start \
  -W -a android.intent.action.VIEW \
  -d "https://example.com/products/123" \
  com.yourcompany.yourapp
```

If your app opens to the product screen, you are done. If Chrome opens instead, there is still a verification problem to investigate.

## Common Mistakes and How to Fix Them

### Wrong SHA-256 fingerprint (the number one issue)

**The problem:** Using the debug keystore fingerprint instead of the Google Play production signing key.

**The fix:** Always get the fingerprint from Google Play Console under App Integrity, not from your local development machine.

### Missing the autoVerify flag

**The problem:** The intent filter exists but without `android:autoVerify="true"`, Android never checks your verification file.

**The fix:** Add `android:autoVerify="true"` to every intent filter that uses the HTTPS scheme.

### The assetlinks.json file is behind a redirect

**The problem:** Your server redirects `example.com` to `www.example.com`, so Android gets a redirect response instead of the JSON file.

**The fix:** Host the file on both domains separately. Android does not follow redirects when fetching this file.

### Package name has the wrong capitalisation

**The problem:** A case-sensitive mismatch between your app's package name and what is in the JSON file.

```json
"package_name": "com.yourcompany.YourApp"   <- This will fail
"package_name": "com.yourcompany.yourapp"   <- This is correct
```

**The fix:** Copy the package name directly from your `build.gradle` file to avoid typos.

### Android 12 strict verification (API 31 and above)

This one catches a lot of developers off guard. In Android 12, Google made verification much stricter. If your app targets `targetSdkVersion 31` or higher and any single domain in your intent filter fails verification, Android disables App Links for all your domains, not just the one with the problem.

Before shipping any update targeting API 31+, run this check:

```bash
adb shell pm get-app-links --user cur com.yourcompany.yourapp
```

Every domain listed must show `verified`. Fix any domain showing `none` or `legacy_failure` before releasing to the Play Store.

## Frequently Asked Questions

### Do App Links work inside TikTok and Instagram?

Not always. TikTok and Instagram run their own in-app browsers which sometimes block standard HTTPS App Links. The workaround is using `intent://` URIs instead, which are more permissive inside those browsers. Read the [TikTok deep links guide](/blog/how-to-create-tiktok-deep-links) for the full breakdown.

### When does Android verify App Links?

Verification happens automatically when your app is installed or updated from Google Play. The result is cached, so your app does not need an internet connection for App Links to work after the initial install. During development, you can trigger re-verification manually with the ADB commands above.

### Can two different apps claim the same domain?

Yes. Add one entry per app in your `assetlinks.json` array. Android will open whichever app the user has installed. If both are installed, it opens the preferred one.

### What happens if I update my assetlinks.json after launch?

Android re-verifies App Links periodically in the background, and app updates also trigger re-verification. For immediate updates during testing, use the `adb shell pm set-app-links` command.

### Do I need App Links for deep linking to work at all?

No. Basic intent filters work without verification, but they always show the "Open with" popup. For any production app where conversions matter, App Links are the right setup.
