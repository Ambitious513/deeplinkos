Here is something that surprises a lot of app developers and creators: when someone taps a link to your website on an iPhone, iOS doesn't automatically open your app. It opens Safari instead. Even if the person has your app installed. Even if you worked hard to build a great in-app experience.

iOS Universal Links fix this. They tell iOS "when someone taps a link to this website, open our app instead of Safari." No popup, no permission dialog, no friction. The user just taps and your app opens. If they don't have your app installed, the link opens in Safari as a normal website — a perfect fallback.

This guide walks you through the complete setup from scratch.

## Why Universal Links Matter for Creators and Brands

If you are sending people from Instagram, TikTok, email, or YouTube to your app, every extra step you add loses you users. Research consistently shows that redirecting through a browser before reaching your app cuts conversion rates by 30 to 50%.

Universal Links remove that step entirely. Someone taps your link in an email, your app opens. They tap it in a DM, your app opens. That is the difference between losing half your traffic and keeping it.

## Universal Links vs Custom Scheme Links

There are two ways to deep link into an iOS app. Here is how they compare:

| What you want to know | Universal Links (https://) | Custom URI Scheme (myapp://) |
|---|---|---|
| Does it show an alert dialog? | Never | "Open in myapp?" every time |
| What happens if app is not installed? | Opens Safari normally | Shows an error |
| Can another app steal your link? | No, domain verified | Yes, any app can claim the scheme |
| Works inside email apps? | Yes | Sometimes |
| Works when typed in Safari? | No | No |
| Minimum iOS version? | iOS 9 and above | iOS 3 and above |

Universal Links win on every dimension that matters for user experience.

## The Three Pieces You Need

Universal Links require three things working together. Think of it like a three-way handshake:

1. **A verification file on your website** called the AASA file, which tells Apple your app is allowed to claim your domain
2. **A setting in your Xcode project** called Associated Domains, which tells your app which websites it owns
3. **A code handler in your app** that decides what screen to show when a Universal Link arrives

If any one of these three is wrong or missing, Universal Links will not work. Let's set up each one.

> **Building for Android too?** The Android version of this is called App Links. The concept is almost identical with a different file and different settings. See the [Android App Links guide](/blog/android-app-links-setup-guide) to set up both platforms together.

## Step 1: Create the AASA File

The Apple App Site Association file (everyone calls it the AASA file) is a JSON file that lives on your website. When someone installs your app, iOS fetches this file to confirm your app is allowed to open links from your domain.

### Where to host it

You need to host the file at both of these URLs on your server. Apple checks both:

```
https://example.com/apple-app-site-association
https://example.com/.well-known/apple-app-site-association
```

**Important:** The file must have no file extension. Not `.json`, not `.txt`. Just `apple-app-site-association` with nothing after it. A lot of people get this wrong.

### What the file looks like

```json
{
  "applinks": {
    "details": [
      {
        "appIDs": ["TEAMID.com.yourcompany.yourapp"],
        "components": [
          {
            "/": "/products/*",
            "comment": "Open all product pages in the app"
          },
          {
            "/": "/blog/*",
            "comment": "Open blog posts in the app"
          },
          {
            "/": "/user/*",
            "comment": "Open user profiles in the app"
          }
        ]
      }
    ]
  }
}
```

Replace `TEAMID.com.yourcompany.yourapp` with your actual App ID (how to find this is explained below) and update the path patterns to match your app's URL structure.

### Finding your App ID

Your App ID is two things combined with a dot between them:

- **Team ID**: Log into Apple Developer Portal, go to Membership, and copy your Team ID (looks like `ABCDE12345`)
- **Bundle ID**: Your app's identifier like `com.yourcompany.yourapp`

Put them together: `ABCDE12345.com.yourcompany.yourapp`

### Serving the file correctly

Your web server needs to return the AASA file with this header:

```
Content-Type: application/json
```

And it must not redirect. If your `example.com` redirects to `www.example.com`, Apple's CDN will not follow that redirect. You need to host the file on both the root domain and the www version separately.

## Step 2: Configure Xcode

Now you need to tell your iOS app which domains it owns.

### Adding Associated Domains

1. Open your project in Xcode
2. Click on your app target in the project navigator
3. Go to the **Signing and Capabilities** tab
4. Click the **+ Capability** button and search for **Associated Domains**
5. Add your domains in this format:

```
applinks:example.com
applinks:www.example.com
```

### For development and testing

Add this version of your domain entry to skip Apple's CDN cache while you are testing:

```
applinks:example.com?mode=developer
```

This tells iOS to fetch your AASA file directly from your server instead of waiting for Apple's CDN to update. Remove it before you submit to the App Store.

### Check your entitlements file

After adding Associated Domains in Xcode, your `.entitlements` file should contain this automatically:

```xml
<key>com.apple.developer.associated-domains</key>
<array>
  <string>applinks:example.com</string>
  <string>applinks:www.example.com</string>
</array>
```

If you do not see it, something went wrong in the Xcode setup step.

## Step 3: Handle the Link in Your App Code

When someone taps a Universal Link and your app opens, your code needs to read that URL and navigate to the right screen. Here is how to do it.

### UIKit apps (AppDelegate)

```swift
func application(
  _ application: UIApplication,
  continue userActivity: NSUserActivity,
  restorationHandler: @escaping ([UIUserActivityRestoring]?) -> Void
) -> Bool {
  guard userActivity.activityType == NSUserActivityTypeBrowsingWeb,
        let url = userActivity.webpageURL else {
    return false
  }
  return handleDeepLink(url)
}

private func handleDeepLink(_ url: URL) -> Bool {
  guard let components = URLComponents(url: url, resolvingAgainstBaseURL: true) else {
    return false
  }
  let path = components.path
  switch path {
  case _ where path.hasPrefix("/products/"):
    let productId = String(path.dropFirst("/products/".count))
    navigateToProduct(productId)
    return true
  case _ where path.hasPrefix("/user/"):
    let userId = String(path.dropFirst("/user/".count))
    navigateToProfile(userId)
    return true
  default:
    return false
  }
}
```

### SwiftUI apps

SwiftUI needs two handlers, not one. Most tutorials only show the first one and miss the second, which causes links to get dropped on cold app launches.

```swift
@main
struct MyApp: App {
  var body: some Scene {
    WindowGroup {
      ContentView()
        // This handles links when the app is already open
        .onOpenURL { url in
          handleDeepLink(url)
        }
        // This handles links when the app launches fresh from a tap
        .onContinueUserActivity(NSUserActivityTypeBrowsingWeb) { userActivity in
          guard let url = userActivity.webpageURL else { return }
          handleDeepLink(url)
        }
    }
  }
}
```

The `.onOpenURL` modifier fires when your app is already running in the background. The `.onContinueUserActivity` modifier fires when your app was not running and gets launched by a Universal Link tap. You need both or you will lose half your deep link events.

## Step 4: Understand How Apple's CDN Works

This is the part most tutorials skip, and it is why debugging Universal Links can feel so frustrating.

Since iOS 14, Apple does not fetch your AASA file directly from your server. Instead, Apple runs a global CDN that fetches and caches AASA files for all apps. When a user installs your app, their device downloads the AASA from Apple's CDN, not your server.

What this means in practice:

- If you update your AASA file, it can take hours or even days before Apple's CDN picks up the change
- You cannot clear this cache yourself
- In production, there is no way to force an immediate update

### How to check what Apple's CDN has cached

Open this URL in a browser, replacing `example.com` with your domain:

```
https://app-site-association.cdn-apple.com/a/v1/example.com
```

If the JSON shown does not match your latest AASA file, Apple's CDN has not updated yet. Use developer mode in your entitlements during development to bypass this entirely.

### Add a Smart App Banner for users who don't have your app

For people who click your link but don't have your app installed, you can show them a native iOS install prompt right in Safari. Add this to the `<head>` of your web pages:

```html
<meta name="apple-itunes-app"
      content="app-id=YOUR_APP_STORE_ID,
               app-argument=https://example.com/products/123">
```

The `app-argument` value is the URL they were trying to visit. After they install your app, iOS opens it directly to that screen. This is Apple's built-in version of deferred deep linking and it costs you nothing to implement.

## Common Mistakes and How to Fix Them

### The AASA file has a .json extension

This is one of the most common issues. Apple will completely ignore a file named `apple-app-site-association.json`. The file must have no extension at all.

### The AASA file is behind a redirect

If your server redirects the AASA file path to another URL, Apple's CDN will not follow it. The JSON must be served directly at the path Apple expects with no redirects.

### Testing by typing the URL into Safari

This one catches everyone. If you type a Universal Link into Safari's address bar, iOS treats that as an intentional request to visit the website, not the app. Universal Links only fire when you tap a link somewhere else, like in Mail, Messages, or Notes.

### The App ID prefix is missing the Team ID

```json
// This will fail silently
"appIDs": ["com.yourcompany.yourapp"]

// This is correct
"appIDs": ["ABCDE12345.com.yourcompany.yourapp"]
```

The Team ID prefix must be included. Without it, iOS will verify your AASA file but never match any app to it.

### The URL path is not covered in your AASA components

If a user taps `https://example.com/checkout/123` but your AASA only covers `/products/*` and `/user/*`, that link will open in Safari. Make sure your components array covers every URL pattern your app needs to handle.

## Pre-Launch Checklist

Run through this before you submit your app to the App Store:

```
AASA file setup:
  [ ] File hosted without .json extension at both paths
  [ ] Content-Type: application/json returned by server
  [ ] No 301 or 302 redirect on the file path
  [ ] Apple CDN validation URL returns the correct content
  [ ] Team ID prefix is correct in appIDs

Xcode setup:
  [ ] Associated Domains capability added
  [ ] Entitlements file contains applinks:yourdomain.com
  [ ] developer mode entry removed before App Store submission

Code setup:
  [ ] UIKit: application(_:continue:) implemented
  [ ] SwiftUI: both onOpenURL and onContinueUserActivity implemented
  [ ] All URL patterns that should open the app are handled

Testing:
  [ ] Tested on a real device (not simulator)
  [ ] Tested by tapping link in Notes or Mail (not typing in Safari)
  [ ] Tested with app installed
  [ ] Tested without app installed (should open Safari)
```

## Frequently Asked Questions

### Why is my Universal Link opening Safari instead of my app?

The three most common causes are: your AASA file is not being found by Apple's CDN yet, the URL path you are testing is not covered in your `components` array, or the user previously tapped the website name in Safari's top bar which disables Universal Links for that domain for that session.

### How long does Apple's CDN take to pick up my AASA changes?

It can be anywhere from a few hours to a few days. During development, add `?mode=developer` to your Associated Domains entry to fetch directly from your server and skip the CDN wait entirely.

### Do Universal Links work inside TikTok and Instagram?

Sometimes. Social platforms use sandboxed browsers that restrict automatic link handling. Universal Links triggered by a real tap (like pressing a button) generally work. Auto-redirects do not. See the [TikTok deep links guide](/blog/how-to-create-tiktok-deep-links) for the complete routing approach for social traffic.

### Do Universal Links work inside my own app's web view?

No. iOS blocks Universal Links inside WKWebView for security reasons. If you need links to trigger Universal Link behavior inside your own web view, use `SFSafariViewController` instead.

### Can my app claim Universal Links from more than one domain?

Yes. Add multiple `applinks:` entries to your Associated Domains and list all relevant domains in your AASA file.
